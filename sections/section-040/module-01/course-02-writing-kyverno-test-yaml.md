# Writing kyverno-test.yaml

`kyverno apply` shows you a result. A test states the result you expect and fails when the actual result is different. The `kyverno test` command finds test files named `kyverno-test.yaml`, runs them and compares. This part explains the test file format and how Kyverno pairs each expectation with an outcome.

## Where the file lives

A test is a directory with a `kyverno-test.yaml` file next to the policy and resource files it uses. `kyverno test .` searches the given path for files with that name. Keep one directory per policy or per feature so each test stays small.

## The Test object

```yaml
apiVersion: cli.kyverno.io/v1alpha1
kind: Test
metadata:
  name: require-limits-test
policies:
  - policy.yaml
resources:
  - resources.yaml
results:
  - policy: require-limits
    rule: check-limits
    kind: Pod
    resources:
      - good-pod
    result: pass
  - policy: require-limits
    rule: check-limits
    kind: Pod
    resources:
      - bad-pod
    result: fail
```

The fields are these:

- `policies` lists the policy files, relative to the test file.
- `resources` lists the resource files.
- `results` lists the expectations. Each has the `policy` name, the `rule` name, the resource `kind`, the resource names in `resources` and the expected `result`.
- `result` is one of `pass`, `fail`, `skip`, `warn` or `error`.

In Kyverno 1.13 the apiVersion is `cli.kyverno.io/v1alpha1`. Older files used `name:` at the top level and `kyverno.io/v1`; the current CLI still reads the older shape, but new files should use the `Test` kind.

## How matching works

The CLI evaluates every rule against every resource. It then looks for an entry in `results` for each outcome. If an outcome has no matching expectation, the test reports it as unexpected. If an expectation has no outcome, the test fails. Both directions matter: a test file is a complete statement of what the policy does to the sample resources.

Autogenerated rules have their own names. A rule named `check-limits` on a Pod also produces `autogen-check-limits` for Deployments. If a test resource is a Deployment, expect the `autogen-` name.

## Reading the output

`kyverno test .` prints a table with one row per expectation: its number, policy, rule, resource and a Pass or Fail column. After the table it prints a total. When a row shows Fail, the actual result differed from the one you wrote, or no result was produced.

> [!TIP]
> **Try it - write and run a test**
>
> In the playground, create `kyverno-test.yaml` for the sample policy and resources with one pass and one fail expectation. Run `kyverno test .`. Then change the expected result of one row to the opposite value and read what the table reports.

## Common pitfalls

- Writing the resource name from the file instead of `metadata.name`. The `resources` list takes the Kubernetes object name.
- Forgetting the `autogen-` prefix for Deployment resources.
- Listing a policy file that contains several policies but writing expectations for only one of them. The other policies produce unexpected outcomes.
